# 运维监控与告警（v10）

本模块适用于当前单 API + SQLite 架构。管理员入口 `/#/admin/operations`，中英日韩四语言。API 启动恢复后检查一次，此后每 60 秒检查；邮件发送队列每 15 秒最多处理一条，也会在检查后尝试发送。检查结果、告警生命周期和发信队列持久化，进程退出时等待在途 SMTP 完成。

## 检查与阈值

| 条件                          | 触发条件                                                                                              | 级别                              |
| ----------------------------- | ----------------------------------------------------------------------------------------------------- | --------------------------------- |
| 资金/资源一致性               | 复用只读 reconciliation 中的余额、冻结、Token/GPU/支付账本、预约关联/重叠、已停占用检查，发现立即告警 | 严重；已记录的欠款/支付审查为警告 |
| 节点无有效心跳                | 最近心跳超过 45 秒或尚未上报，持续观察 5 分钟                                                         | 警告                              |
| 采集/运行环境预检、GPU 缺失   | 在线节点库存错误、Docker/当前模式运行环境不可用或已知 GPU 缺失，持续观察 5 分钟                       | 警告                              |
| 部署未收敛                    | queued/starting/checking/draining/stopping/unknown 持续观察 5 分钟                                    | 警告                              |
| 部署失败                      | failed 立即告警，stopped 后恢复                                                                       | 严重                              |
| 已上架 managed 模型无健康路由 | 持续观察 5 分钟；不主动请求外部推理服务                                                               | 警告                              |
| HTTP 5xx 比例                 | 近 5 分钟对应分组完成数 ≥20 且 5xx ≥10%                                                               | 严重                              |
| 平台 API 平均耗时             | 近 5 分钟完成数 ≥20 且均值 ≥2000ms；不套用到推理和 Agent                                              | 警告                              |
| 最终推理失败                  | 近 5 分钟创建且已结束的持久化请求 ≥20，failed ≥10%，包含 HTTP 200 后的 SSE 失败                       | 严重                              |
| 检查/部署控制循环失败         | 立即告警；检查失败保留原告警，不宣称异常已恢复                                                        | 严重                              |

观察起点以首次扫描到条件为准，间隔最多增加一分钟发现延迟。无工作负载的维护/禁调度节点不产生离线与库存告警；仍承载部署的节点继续检查。GPU 温度、容量和占用使用已有真实采集展示，不凭未知硬件编造温度阈值或性能目标。缓存磁盘等预检失败通过库存/运行环境异常提示，当前没有完整的主机磁盘、网络、进程指标时序库。

资金检查不调用带欠款结算逻辑的业务事务，不修改账户、订单、账本或资源。运维模块的事务只写运维表；确认告警也不扣款、止损、停机或释放 GPU。清理和退款仍沿用原部署/订单协议。

## 生命周期

- `(code, entityId)` 在未恢复期间唯一。先保存 detectedAt，持续达到阈值后写 openedAt；短暂条件消失时删除未触发的候选，不发邮件。
- 达阈值首次触发和自动恢复各产生一个事件；同一异常持续扫描、数值变化和确认已阅不重复发邮件。
- 确认记录首位管理员 ID 与时间；重复确认幂等，确认不等于恢复。不存在人工“清空异常”的接口。
- 条件消失后写 resolvedAt 并保留历史、确认信息；以后再次出现生成新的告警 ID。控制面重启保留首次观察时间、未恢复记录和通知队列。
- 一轮扫描的新告警/恢复合并为一封摘要，包含固定诊断名称、严重性、关联 ID、告警 ID、UTC 时间和固定管理页链接，不包含账户邮箱、余额、prompt、原始 Docker 输出、节点凭证或 SMTP 错误详情。

## HTTP 指标与探测

对平台 API、`/v1/` 推理网关、`/api/agent/` 分开统计已完成数量、5xx 数/比例、平均响应耗时，断开连接单独计数。使用服务端单调计时测量 HTTP 响应时间；近 5 分钟秒级桶最多保留 300 个。连接结束不等于推理结算结束，SSE 的最终错误另检查持久化请求记录。

指标来自当前进程，重启归零；不足 20 个完成样本不触发比例/平均耗时告警。持久化最后检查信息不是长期指标时序库。管理页每 15 秒刷新，翻阅后续历史页时暂停自动回到第一页，可手动刷新。

响应带服务端随机 `X-Request-ID`；5xx 日志记录请求 ID、分组、HTTP 状态和耗时，不记录 URL 查询、Cookie、密钥、请求体或用户 prompt。

`GET /api/health` 只返回 `{ok}`。检查最近两分钟未成功、当前检查失败或部署控制循环失败时返回 503，否则 200。资金异常有独立告警，不把业务资金问题等同于进程不可用。必须从独立主机/监控服务探测此接口：进程停止、主机断网或 SQLite 不可写时，平台不能依靠自己的定时器发送停机告警。当前未部署外部探测器，不承诺已取得生产可用性监测证据。

## SMTP 配置与失败

复用现有 SMTP TLS/STARTTLS、固定 PUBLIC_ORIGIN 和有限超时。在环境变量设置：

```dotenv
OPS_ALERT_EMAIL=实际受控收件人邮箱
OPS_ALERT_LOCALE=zh-CN
```

语言可选 zh-CN/en-US/ja-JP/ko-KR，默认中文。单一收件地址；配置收件人但未配置 SMTP 时拒绝启动。收件人留空则仍持久化并展示告警，不生成邮件队列，也不在以后补发该期间的历史事件。

通知先落盘，SMTP 前递增尝试次数。失败按 2/4/8/16 分钟退避；每轮最多 5 次，失败后在管理员页面显示固定 smtp_failed 诊断，可通过 CSRF 写接口重试。重试保留原事件时间和载荷。超过 24 小时的摘要标为 expired，不再重发陈旧事件；收件人变更时旧队列标为 recipient_changed，不把旧摘要转发给新收件人。

SMTP 返回接受后标为 sent，界面显示“SMTP 已接受”，不代表到达收件箱。SMTP 接受后、数据库保存前宕机可能重复一封邮件，不能宣称恰好投递一次。未接入邮件服务商回执或退信 Webhook；真实收件、垃圾邮件和限额须在受控环境验收。当前测试仅模拟 SMTP，没有发送真实邮件。

## 数据与接口

v10 增量迁移创建 ops_alerts、ops_checks、ops_notifications 及未恢复唯一索引/待发索引，不改变历史业务数据。运维历史保留在库中；备份按现有一致性备份流程。当前不自动删除告警或通知历史，容量增长后需制定归档保留策略。

| 方法与路径                                                       | 权限与语义                                                                                                                                                                                       |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| GET `/api/admin/operations?state=active或resolved&before=cursor` | 管理员；默认 active。告警每页 50 条，nextCursor 为 null 到底；含全量 active/unacknowledged/resolved 计数、检查状态、当前指标、待发/失败计数及最近 50 条通知状态。无通知载荷/收件地址/SMTP 配置。 |
| POST `/api/admin/operations/alerts/:id/ack`                      | 管理员 + CSRF；首次确认留痕，重复调用幂等；已恢复记录不覆盖确认。                                                                                                                                |
| POST `/api/admin/operations/notifications/:id/retry`             | 管理员 + CSRF；仅失败、未过 24 小时、仍为原收件人的通知重入队；未配置返回 503，过期/改收件人返回 409。                                                                                           |

关联 ID 与诊断码保留原始技术值，显示名称和状态翻译为四语言。财务 expected/actual 按 CNY 微元格式化，数量、百分比和毫秒使用对应单位。

- 13 项专项测试：资金只读、持久化生命周期、确认/复发、节点与部署阈值、维护抑制、模型路由、检查失败保留、分组指标、SSE 最终错误、四语言摘要、SMTP 去重/重试/过期/收件变更、重启、分页、鉴权/CSRF 与 health。
- 全套 107 项 Node 测试、TypeScript/生产构建通过。Go 协议未变，本模块不以控制面测试代替 GPU 真机验收。
- Chromium 验证四语言、375px 布局、确认不清除异常、失败邮件重试、恢复历史保留确认与模拟通知；独立内存库，不写日常账本。
- SMTP 真实投递、外部健康探测、生产负载阈值校准及真实 GPU 故障告警仍待环境验收。
