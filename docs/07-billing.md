# CoreMatrix 计费与账本

共享模型按实际输入和输出 Token 计费，独享算力按明确的资源时段计费。共享 Token 与 GPU 按卡时长账本，以及 Stripe 在线充值均已实现；商户收款与真实 GPU 验收仍待环境配置。

## 已实现的 Token 金额

1 元等于 1,000,000 微元；模型 inputPrice 和 outputPrice 是每百万 Token 的微元单价。

```text
amountMicros = ceil(
  (inputTokens × inputPriceMicros + outputTokens × outputPriceMicros)
  / 1,000,000
)
```

计算使用 BigInt 中间值，最终金额校验在安全整数范围。输入 1,200 Token、输出 600 Token，单价分别为每百万 2 元、6 元时，实际费用为 6,000 微元，即 0.006 元。该示例仅说明规则，不能写死到业务流程。

## 余额和预留

| 名称          | 含义                                     |
| ------------- | ---------------------------------------- |
| users.balance | 总未消费余额，含处理中请求尚未结算的部分 |
| heldBalance   | Token pending + GPU 订单 + 预约 reserved 总和          |
| API balance   | 无争议时为 max(0, users.balance − heldBalance − paymentDebt)，争议处理中为 0 |
| tokenSpend    | 当前 UTC+8 请求开始日的成功消费金额      |
| dailyBudget   | 用户设置的每日 Token 消费上限            |

预留按模型配置的输入上限 contextTokens 和本次 max_tokens 计算最大费用。该策略不依赖客户端估计 Token，但可能预留较多资金，UI 必须解释。

处理请求时在同一事务中检查当前可用余额与预算，并写入 pending 请求。预算占用包含当日 pending 预留和 succeeded 实际金额。

## 成功和失败

成功结算事务包含扣减用户余额、插入唯一消费账单、把请求改为 succeeded、保存结果及价格快照、清除 reserved。任一步失败不能只完成其中一部分。

上游拒绝、超时、响应过大、缺失 usage、Token 越界或回复格式无效时，不向用户扣款，释放预留并保存失败结果。平台可能已承担上游成本，后续可计入异常运营成本，但不能伪造用户成功账单。

流式和非流式网关均不接受客户端上报的 Token 数。Agent 心跳和健康探测也不能直接产生用户账单。

## 流式请求（已实现）

SSE 文本增量为暂存结果，收到合法 finish_reason、可信最终 usage 和 `[DONE]` 后复用同一结算事务，写唯一账单与完整回复，再向客户端发送带 billing 的最终帧。停止接收或关闭页面不取消服务端生成，包括后续生成在内的最终用量仍须付费；默认总调用超时 60 秒。缺少可信最终用量、超时或格式错误则失败解冻，不按已显示文字估算费用。平台承担这类上游异常成本。

断线后查询本人原请求状态，不自动使用新 Key 重发；成功 SSE 重放由已保存回复生成，不重新推理。正常进程关闭等待在途请求结算后再关闭数据库。强制终止仍遵守启动时失败解冻规则。完整契约与验证见 [流式推理与计费](14-streaming-billing.md)。

## 幂等与重试

去重范围为 `(userId, Idempotency-Key)`，同时比较请求内容指纹。

| 已存状态        | 重复请求行为                             |
| --------------- | ---------------------------------------- |
| pending         | 返回 409 request_pending，不再调用上游   |
| succeeded       | 返回保存的成功结果，不再扣款             |
| failed          | 返回保存的失败结果；主动新尝试使用新 Key |
| 同 Key 不同内容 | 409 idempotency_conflict                 |

浏览器因网络中断无法确认结果时保留原 Key。请求已经发到推理服务后，首版网关不自动换实例重发，避免生成两次而状态不明。

## 跨日和改价

请求按开始日归入 UTC+8 日期；午夜前开始、午夜后完成的请求仍计入开始日预算和消费。所有创建、结算和汇总保持同一口径。

模型价格在请求开始时快照。模型改价、下架、模板修改和部署切换均不影响在途请求的金额。历史账单按自己的 inputPrice/outputPrice 展示，不能重新读取当前模型价格计算历史费用。

## 人工入账

已支持 Stripe 回调在线入账和管理员人工入账。人工入账必须记录目标用户、微元金额、reason、reference、actorId 和时间。reference 唯一，同内容重试只返回成功一次，不重复加钱。

净消费收入统计包括成功 Token、GPU 扣款及 GPU 退款，不含充值。人工入账是预收款或授信记录，不计入模型收入。原始说明属于用户数据，国际化时不自动翻译或替换。

## 与部署的衔接

受管部署选择和费用预留在一个明确的请求开始流程中完成。requests 增加 deploymentId，结算仍使用当前账本事务。

部署 draining 后不接受新请求，已有 pending 请求继续使用原目标完成。停止容器前需确认该部署没有在途请求；节点离线或容器异常引起的请求失败按原失败规则处理。

不存在健康部署时返回 503，不写成功账单、不调用错误模型，也不把失败请求当作零价成功。

## GPU 按卡时长计费（已实现）

下单原子冻结款项和资源，Jupyter 健康且节点确认到期保护后扣款；启动失败解冻，到期停止并确认资源回收，提前停止按已用秒数结算退款。金额、状态、幂等、退款和异常恢复以 [GPU 购买与计费](12-gpu-rental-billing.md) 为准。

独享环境里的计算不额外收取共享 Token 费用；该用户另行调用平台共享模型 API 时，仍按模型 Token 价格收费。

## 在线支付（已实现）

创建支付单不会直接给用户增加余额。只有服务端验签后的支付回调，确认商户、订单、币种、金额和交易状态后，才能通过唯一支付交易号原子入账。浏览器跳转成功页不能作为到账凭据。

已实现重复/乱序/伪造回调、每笔退款状态、失败/取消恢复、争议与恢复、保护冻结款项的欠款补偿及持久化幂等。充值入账与消费账本分开，不能将支付金额重复计为模型收入。credits 为 recharge 减 recharge_refund 的净入账，recharge_refund 负数代表恢复信用。完整接口和渠道验收见 [Stripe 支付](16-stripe-payments.md)。

## 成本和对账

已实现实际成本单据手动采集、设备/电费/带宽/存储/运维/上游等分类、关联服务器、作废留痕与期间汇总。毛利仅按已录入成本计算；没有有效成本记录时不展示虚构毛利。自动采集仍需真实设备成本、电表或供应商账单来源。接口与边界见 [全量交付核查](13-delivery-status.md)。

总毛利 = 已确认消费收入 − 同口径运营成本。部署数量、GPU 分配比例、利用率和收入不是可互换指标。

必须能核对：用户净入账减成功净消费等于存储余额减 paymentDebt；无欠款/争议时可用余额加预留等于存储余额；每条成功请求恰有一条消费账单；预留总和不为负。发生差异时告警并保留原记录，不用覆盖余额来掩盖原因。

## 固定时段预约计费

预约时冻结最高报价，不预先启动或扣费。到时原子转为交付订单，健康起算并等待节点到期确认；截止保持原计划，启动延迟部分不收费。未按时交付解冻，取消/退租继承确认清理后退款。即时租用、续费和管理员无期限分配均不得侵占已有时段。预约金额是报价上限，实际金额写关联订单及账本，详见 [预约契约](17-gpu-reservations.md)。
