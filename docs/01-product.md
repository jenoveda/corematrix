# CoreMatrix 产品需求

平台通过统一模型接口销售 Token 服务，同时管理自有 GPU 服务器及其运行的模型。先完成“用户调用并计费”和“管理员管理服务器与部署”的闭环，现已开放余额购买整卡 JupyterLab，Stripe 在线支付已实现，商户环境待验收。

## 多语言要求

用户端和管理端首期支持简体中文、英文、日文、韩文。包括全部固定文案、错误、校验、空状态及无障碍标签；金额仍为 CNY，业务时区仍为 UTC+8。实施细节见 [国际化](10-i18n.md)。

## 用户和权限

| 角色     | 可执行操作                                                   | 不允许的操作                                             |
| -------- | ------------------------------------------------------------ | -------------------------------------------------------- |
| 访客     | 注册、登录、查看已上架模型                                   | 查看私人钱包、调用付费模型、进入管理台                   |
| 普通用户 | 查看自己的钱包、设置预算、管理 Key、调用模型、查看自己的账单 | 修改价格、给钱包入账、管理服务器和部署、查看其他用户数据 |
| 管理员   | 用户能力，以及模型、服务器、部署、人工入账和运营汇总         | 读取用户密码明文或导出已有 Key 明文                      |
| Agent    | 本节点心跳、GPU 数据、领取和回报本节点任务                   | 用户账本、其他节点任务、模型价格和管理员接口             |

普通注册不接收角色或初始余额。管理员由服务器维护者初始化；浏览器切换“运营管理台”不能赋予权限。

## 核心流程

### 用户使用共享模型

1. 注册并登录，初始余额为零。
2. 管理员按已确认款项或授信入账；在线支付接入后改由支付回调入账。
3. 查看已上架模型、输入输出单价与可调用状态。
4. 在线体验或使用 API Key 发起请求，网关检查身份、模型和费用预算。
5. 服务端预留最大费用，调用真实推理服务。
6. 根据实际 usage 结算，钱包展示剩余可用余额及账单。

验收重点：修改浏览器数据不能增加余额；同一请求重试不重复收费；余额不足不请求上游；请求失败不会生成成功消费账单。

### 管理员添加服务器

1. 填写节点名称、区域、可达的推理主机地址及允许端口范围。
2. 平台生成节点 ID 和一次性展示的 Agent Token，节点状态为“等待接入”。
3. 运维在指定 Linux GPU 主机安装 Agent，配置平台 URL 和本节点凭证。
4. Agent 验证驱动、Docker 和 GPU 能力，上传真实库存与运行状态。
5. 管理台展示在线状态、GPU UUID、显存和占用；异常设备不可调度。

登记成功不代表服务器在线。GPU 数量以 Agent 上报为准，不允许管理员手填实时 GPU 指标。

### 管理员部署模型

1. 在模型管理中配置可复现的模型来源和经过校准的资源模板。
2. 选择在线服务器及空闲 GPU，确认模型版本和运行参数。
3. 后端原子预留 GPU 和端口，生成部署与持久化启动任务。
4. Agent 领取任务、启动指定容器、回报进度和健康结果。
5. 控制面检查实际推理可达性及模型身份，合格后加入网关路由。
6. UI 展示“就绪”及节点、模型、GPU、启动时间与最近健康时间。

仅有任务提交成功、容器进程存在或 Agent 心跳均不能判定模型可调用。

### 切换服务器运行的模型

首版采用滚动切换，需要新旧实例并存的资源。资源不足时返回清晰错误，不能暗中停止旧模型腾卡。

1. 选择旧部署和目标模型；校验新模型可部署且新资源未被占用。
2. 保留旧部署接流，启动并检查新部署。
3. 新部署就绪后启用新路由，并让旧部署停止接收新请求。
4. 等待旧部署在途请求结束，再发送停止任务。
5. 只有 Agent 确认容器退出后才释放旧 GPU 和端口。

若目标是不同模型 ID，旧模型不会自动冒充新模型：新请求仍按用户指定的模型 ID 路由。旧模型最后一个实例退役后，旧模型的新请求返回不可用，除非它还有其他健康实例。

### 部署失败

切流前新实例失败，旧服务继续运行；新资源只有确认清理后才释放。切流后旧容器停止失败，旧部署保留“清理失败”状态及资源占用，并允许重试清理。节点离线时不宣称清理成功。

## 页面功能清单

用户端保留模型广场、独享算力、API 与用量、钱包账单、注册账户五个入口。独享算力支持选择卡数及整小时数，余额购买并自动到期回收；规则见 [GPU 购买与计费](12-gpu-rental-billing.md)。

管理端保留运营概览、算力服务器、模型部署、模型与定价、收入成本五个入口。下一阶段在现有服务器和部署入口增加列表、详情和操作，不引入第二套管理应用。

## 业务规则

| 编号 | 规则                                                             |
| ---- | ---------------------------------------------------------------- |
| BR01 | 已登记、在线、可调度、模型就绪是不同状态                         |
| BR02 | GPU 原子预留，任何一个活跃占用都不能重复出售或分配               |
| BR03 | GPU 利用率低不代表 GPU 空闲；是否已分配以资源账本为准            |
| BR04 | 显存阈值来自模型版本、精度、上下文和真机测量，不按参数量直接猜测 |
| BR05 | 模型上架是商业开关，健康实例是运行条件，两者都满足才可调用       |
| BR06 | 没有健康路由时先失败，不预留用户费用或伪造模型回复               |
| BR07 | 费用由服务端可信用量计算，客户端不能传金额要求扣款               |
| BR08 | 充值和人工入账不是已确认的模型收入                               |
| BR09 | 部署和 Token 请求分别使用自己的幂等键，不能混用去重范围          |
| BR10 | 删除节点、模型不能级联删除历史账单或正在运行的容器               |
| BR11 | Token 定价按请求开始时快照，后续改价不追溯历史                   |
| BR12 | 实际硬件不可用时显示离线或未知，不用样例数据替代                 |

## 首版质量要求

鉴权、越权、并发 GPU 预留、任务重复执行、健康检查、失败恢复和收费一致性必须有自动化测试。GPU 真机验收至少覆盖一个单卡模型和一个多卡实例；具体模型与并发性能以可用硬件实测确定。

交互支持桌面和 375px 窄屏。长表格可在表格区域横向滚动，不能使整个页面溢出；表单有标签、错误反馈和提交中状态。

节点心跳、任务超时等默认值见 [服务器和模型部署](05-agent-deployment.md)，均为首版工程参数，不构成已测量的性能承诺。
