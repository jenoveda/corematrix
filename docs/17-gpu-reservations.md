# GPU 预约（C03，已实现，真机仍待验收）

本模块在已有整卡 JupyterLab、余额计费、续费和退租基础上增加未来预约。用户选择资源池、卡数、开始时间和小时数，下单冻结最高报价，到预约时间才分配物理资源和启动容器。预约不能替代 GPU/端口的实际停止确认，不会因为日历到时就强行把仍运行的卡卖给下一位用户。

## 时段和收费规则

- 开始时间为服务端当前时间后 5 分钟至 30 天，时长 1–720 整小时、1–64 同机同型号且同显存 GPU。表单明确使用 UTC+8，即使浏览器在其他时区也按 UTC+8 转为 UTC ISO 提交；语言切换不改变时间。
- 窗口固定为 `[startsAt, endsAt)`，endsAt = startsAt + hours。健康交付延迟不会顺延结束时间；价格沿用预约时保存的快照，不受后续改价或关闭新销售影响。
- 报价上限 = 单卡小时价 × 卡数 × 小时数，全部冻结。预约前不启动容器，不占物理 gpu_allocations，不提前收消费费。
- 到时创建订单、启动任务和物理占用，并原子把冻结从预约转到交付订单，不重复冻结。首次 Jupyter 健康时记实际 startedAt，截止保持固定，待 Agent 保存该截止并确认后才扣款/开放入口。
- 实际交付秒数 = ceil((endsAt − startedAt) / 1000)，实际费用 = ceil(小时微元价 × 卡数 × 交付秒数 / 3600)。只扣实际交付到固定截止的费用，其余冻结释放；钱包的 GPU 账单显示计费用时。
- 从 startsAt 起 20 分钟内仍未完整交付，不能再激活或收费。控制面每 15 秒检查，失败解冻并清理；控制面离线后恢复已错过期限的预约直接失败，不补发一份过期服务。停机确认以前物理资源继续保留。
- 预约窗口后预留 5 分钟清理间隔，不收费；清理实际超过间隔时仍不释放物理占用，下一预约最多等待至交付截止，不能双卖。该间隔是计划裕量，不是清理成功保证。

后续经用户主动续费并通过资源冲突检查时，可以延长已交付预约的截止；原预约开始、型号和单价保留。余额欠款/支付争议在启动前仍未解决时，取消该次交付并解冻。已进入交付过程的冻结资金继续受既有付款保护规则约束，详见支付契约。

## 时间与资源计划

预约按具体 GPU UUID 和端口保存计划，用户只见资源池、型号、显存、卡数和时间，管理员可见计划的 UUID/端口。未来预约不会从当前时间起锁住空闲 GPU：足够短的即时订单仍可在预约前使用同一资源。

可供预约的节点必须当前在线、库存可信、可调度、非维护，具备 Docker、有效 Jupyter 镜像 digest、workspaceReady、expirySupported 及有效密钥配置；只允许 gpu-rental 节点及与控制面不同的 Jupyter 主机，生产要求 HTTPS。未知、丢失、外部占用的 GPU 不出售。

对当前物理占用采用保守结束预测：

| 占用类型                                      | 计划上何时可复用                           |
| --------------------------------------------- | ------------------------------------------ |
| 已交付、有限期付费订单                        | 当前承诺到期后加 5 分钟                    |
| 尚未健康的立即购买                            | 下单后 20 分钟启动裕量 + 购买时长 + 5 分钟 |
| 尚未健康的固定时段预约                        | 固定 endsAt + 5 分钟                       |
| 手工无期限环境、推理实例、停止/失败未确认清理 | 没有可承诺释放时间，不作为未来可售资源     |

这些预测只用于承诺日历容量；真正启动仍经过 gpu_allocations/port_allocations 唯一索引、实时库存、健康和任务租约校验。当前占满但已知会到期的付费卡可以提前预约；未知释放时间不能伪造成可用。

同一事务内选卡、选端口、核对窗口并写预约。相邻预约必须留足清理间隔。即时购买按最长启动裕量检查未来承诺；续费同时检查原卡和端口，冲突时 409 且不追加扣费。管理员无期限分配也不能越过已有预约，通过请求体伪造期限/预约 ID 不能绕过内部调度上下文。

有未执行预约时，节点不能删除或改变主机、端口范围、工作模式。价格、名称和销售开关仍可变，既有预约使用快照；维护/禁用可能造成交付等待或失败，管理员应先在预约计划中取消并填写用户可见原因。调度器不擅自改到另一台机器、型号、显存或其他卡；原 UUID 的库存信息变化时等待修复，超时失败解冻。

## API

所有接口需要 Cookie 会话，POST 要求 CSRF；API Key 不具备钱包购买和预约权限。管理员路径另校验角色。

| 接口                                             | 请求 / 结果                                                                                |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------ |
| GET /api/compute/offers?hours=N                  | 对当前开始、最长 20 分钟启动裕量计算立即购买目录，默认 hours=1                             |
| GET /api/compute/offers?hours=N&startsAt=UTC_ISO | 对未来固定窗口计算目录，可包含当前已出租但在预约前会释放的卡；仍不暴露 UUID/主机           |
| POST /api/compute/reservations                   | Idempotency-Key；`{offerId,cards,hours,expectedHourlyPrice,startsAt}`；202 `{reservation}` |
| GET /api/compute/reservations                    | `{data}`，仅本人记录                                                                       |
| GET /api/admin/compute/reservations              | `{data}`，全部记录，管理员资源计划                                                         |
| POST /api/compute/reservations/:id/cancel        | 本人，body `{}`；202 当前预约；他人和不存在均 404                                          |
| POST /api/admin/compute/reservations/:id/cancel  | 管理员，`{reason}`，1–200 字符，用户可见；202 当前预约                                     |

startsAt 为严格有效的 UTC ISO，例如 `2026-10-17T02:00:00.000Z`（UTC+8 10:00），接受带 `.000` 或完整秒的 Z 格式，不使用含糊本地时间。小时、卡数、价格等以原购买接口的整数边界校验。客户端不能指定用户、冻结金额、实际 GPU/端口、交付订单或调度豁免。

幂等范围为 `(userId,requestKey)`，比较标准化时间与原报价/数量。相同键和内容返回原预约，即使时间已过、已交付或取消；不同内容 409 idempotency_conflict。取消可重复请求，保留第一次取消操作者/理由，不重复返还或停止。资源冲突返回 reservation_conflict 或现有 offer_unavailable，价格变化 rental_price_changed，余额不足 insufficient_balance，时间非法 reservation_time_invalid。

Reservation DTO 为 id、serverName、resource、memoryMiB、cards、hours、hourlyPrice、amount、reserved、status、startsAt、endsAt、createdAt、closedAt、errorCode、cancelReason、orderId。amount 是预约报价上限，不是最终扣款；实际费用见对应 Order/账本。管理员另有 email/serverId/gpuUuids/port。

GET /api/state 新增本人 reservations，管理员另有 reservationSchedule；Order 新增可空 reservationId/scheduledStart/scheduledEnd。旧立即购买订单三项均为空，返回及计费兼容。目录 GET 的 hours 必须与意图时长相同，POST 仍以服务端最终检查为准。

## 状态和取消

```text
booked → starting → active → stopping → completed
booked → canceled
booked → failed
starting → stopping → canceled（主动取消且未收费）
starting → stopping → failed（交付失败且未收费）
```

booked 仅冻结报价。starting 已创建交付订单/占用但尚未扣款。active 已健康并确认到期保护。stopping 表示停止和清理中，不能直接复售；closedAt 在确认清理后才写。管理员或用户取消与到时调度竞争时，读取事务内的当前阶段：未启动直接释放全部冻结；已经启动则停止，已交付按实际用时精确结算，确认清理后退回未使用费用。文件保留。

正常到期后，原 Go Agent 4-go 到期保护继续使用同一固定 expiresAt/revision，不要求 Agent 理解预约日历。续费仍需新 revision 落盘确认，不能跨过其他预约窗口；续费未确认到旧截止仍停止和退款。通过已有关联订单发起取消，也同步更新预约状态和取消来源。提前清理完成后释放剩余计划窗口，其他用户可再次预约该时间。

## 持久化、恢复和对账

schema v9 新增 rental_reservations，保存报价、冻结、UUID/端口时间计划、状态、取消和唯一交付关联。rental_orders 增加 reservationId/scheduledStart/scheduledEnd，唯一索引确保一个预约只有一个订单。原用户、密码、余额、账本和订单不重算。

钱包冻结为 Token pending + 当前订单 reserved + 预约 reserved。预约转交付用同一个事务，不能在中途短暂解冻或重复冻结。取消、超时释放同样在事务内，支付欠款只从未冻结资金偿还，不侵占正在履约的预占。

控制面恢复保留预约冻结与计划；到时以事务内状态调度，状态 starting/active 的预约不会重新创建订单或容器。内部交付幂等键使用不可从公共接口提交的保留命名空间，避免与用户购买请求键碰撞。价格更改、接口重试和进程重启不产生第二条消费账单。

只读对账新增预约冻结金额、订单反向关联/型号报价/时间和 GPU/端口计划重叠检查。问题只记录和展示，不覆盖余额或自动删计划。预约历史目前与现有订单一起通过快照返回；当前适用单 API/SQLite 与有限自有节点，历史规模扩大时需统一分页或归档，不宣称多实例和无限历史高并发已验收。

## 页面与验证

用户“独享算力”在原购买表单中选择未来预约、UTC+8 日期、卡数、时长，展示报价上限、冻结、预约列表和交付订单。管理员“算力服务器”显示预约计划、资源详情与带理由的取消弹窗。中英日韩均覆盖状态、错误、说明与金额。

即时购买与预约共用用户范围 sessionStorage 保存原请求键和参数；未知响应后锁定参数，关闭/刷新可原单重试。存储不可用时不发起新购买，显示允许会话存储及核对已有订单的提示。语言切换不触发下单或清空草稿。

自动测试包含预约权限/CSRF、有效 UTC 时间、报价冻结、幂等与隐私、并发重叠、卡和端口、清理间隔、当前满载的未来可用、即时短租/管理员分配/续费保护、延迟少收费与固定截止、取消及清理、支付争议、库存变化、超时无收费、提前退租、冷启动与只读对账。新增 15 项预约专项，全套 94 项 Node 测试与构建通过；浏览器专项在 Los Angeles 时区验证 UTC+8 提交、四语言、375px、丢失响应刷新恢复、取消理由保留、延迟交付与退租回收，存储拒绝时无新订单。

测试使用独立内存数据库、本地 Jupyter 健康服务和协议夹具。没有可用 Linux/NVIDIA 测试节点，真实 GPU、Docker、TLS/WebSocket、离线到期与硬件恢复仍须 H01–H07 验收；不能用上述模拟证据替代。
